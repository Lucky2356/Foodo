## Задание для Claude

Ты — опытный full-stack разработчик, архитектор и продуктовый дизайнер. Создай **Foodo** — самостоятельный работающий сервис планирования питания, функционально похожий на публично описанный Youamm и доступный всем пользователям бесплатно. Нужен полноценный проект с кодом, данными, проверками и инструкцией развёртывания.

### 1. Цель и принятые решения

Помочь человеку или семье ответить на три вопроса: что готовить, сколько готовить и что покупать. В одном месте должны работать меню, рецепты, расчёты порций, КБЖУ, остатки и покупки.

Для этой версии «открытое для всех» означает:

- публичный доступ по ссылке;
- все основные функции бесплатны, без подписок, пробных периодов, оплаты и искусственных платных ограничений;
- полноценное использование в гостевом режиме без обязательной регистрации;
- необязательный аккаунт для синхронизации между устройствами;
- отсутствие требования Telegram, приглашения или принадлежности к организации.

Публичный сервис не означает публичность личных меню и профилей. Данные пользователей приватны. Публикация исходного кода и выбор open-source лицензии — отдельное решение владельца; не трактуй бесплатность как согласие на такую публикацию.

Первый релиз: адаптивный сайт и устанавливаемое PWA для компьютера и телефона. Нативные Android/iOS-приложения в первый релиз не входят. Не называй PWA APK или приложением из App Store. Telegram Mini App — следующий этап после работающего основного продукта.

Утверждённое название — **Foodo**, произношение «Фудо», техническое имя проекта `foodo`. Используй Foodo в интерфейсе, заголовках страниц, PWA manifest, документации и безопасных примерах конфигурации; основное название вынеси в конфигурацию. Имя домена и доступность товарного знака этим заданием не определяются. Интерфейс полностью на русском, единицы метрические, валюта по умолчанию рубли. Не привязывай сервис к конкретной семье, городу или диете.

Используй Youamm как функциональный ориентир. Создай собственные тексты, дизайн и данные. Не копируй чужие фотографии, статьи, логотип, базу рецептов или бренд. Не обращайся к закрытым API и не пытайся обходить авторизацию референса.

### 2. Технологии и способ работы

Предпочтительный стек:

- backend: Python, Django, Django REST Framework;
- база данных: PostgreSQL;
- frontend: React, TypeScript, Vite;
- встроенная Django Admin для управления справочниками, рецептами и статьями;
- OpenAPI-документация API;
- Docker Compose для приложения, базы и прокси;
- GitHub Actions для тестирования и сборки.

Проверь совместимость выбранных стабильных поддерживаемых версий по официальной документации. Зафиксируй зависимости и lock-файлы. Не добавляй Redis, очереди, отдельные микросервисы или платные провайдеры без конкретной необходимости.

Главный принцип: сервис работает без LLM и платного AI API. Меню формируется алгоритмом на основе структурированных рецептов и ограничений. Не используй языковую модель как источник числовых КБЖУ, аллергенов или медицинских назначений.

Храни проект в одном репозитории с понятными каталогами backend, frontend и docs. Не требуй установки инструментов на компьютере владельца для обычной сборки: основной путь — репозиторий и GitHub Actions. При этом приложи Docker-команды для разработчиков и для сервера.

Если доступен рабочий репозиторий и терминал, создавай файлы и запускай проверки. Если есть только чат, честно сообщи ограничение и выдавай полные файлы по этапам. Не изображай выполненные коммиты, тесты или деплой.

### 3. Пользовательские экраны

Реализуй:

1. Главную страницу с объяснением возможностей и кнопкой «Составить меню бесплатно».
2. Первоначальную настройку: семья, цель, уровень готовки, ПП/обычное питание, повторяемость, техника, исключения, магазин, бюджет, учёт витаминов. Расширенные шаги можно пропустить; настройки сохраняются и редактируются позже.
3. Меню на день и неделю с переключением участника семьи.
4. Публичный каталог рецептов, поиск и фильтры.
5. Полную карточку рецепта.
6. Список покупок.
7. Остатки продуктов дома.
8. Профили участников семьи и настройки питания.
9. Избранное и историю сохранённых меню.
10. Дневник воды и простые отметки выполнения привычек.
11. Вход, регистрацию, восстановление пароля и настройки аккаунта.
12. Небольшой раздел статей, страницу контактов и сведения об обработке данных.

На телефоне — удобная нижняя навигация между меню, рецептами, покупками и профилем. На компьютере — навигация и обзор недели. При ширине 360 px основные действия должны быть доступны без горизонтальной прокрутки страницы.

Дизайн спокойный, с понятной типографикой, карточками блюд, крупными кнопками и видимыми состояниями загрузки, ошибки и пустого результата. Цвета и композиция собственные. Не размещай выдуманные отзывы, оценки, число пользователей или обещания похудения и экономии.

### 4. Гостевой режим и аккаунт

Без регистрации доступны создание семейных профилей, генерация и ручное редактирование меню, рецепты, избранное, покупки, остатки, вода и экспорт.

Гостевые данные сохраняй в IndexedDB на этом устройстве. Объясни коротко, что без аккаунта синхронизации нет, а очистка данных браузера удалит локальные записи. Создай резервный экспорт и импорт пользовательских данных в JSON.

Профили, вес, возраст и исключения гостя не отправляй на сервер: генератор гостевого меню работает локально с общедоступной базой рецептов. Зафиксируй единые контракты и одинаковые тестовые примеры для локального и серверного расчёта. Не допускай расхождения результатов из-за двух несогласованных реализаций.

У аккаунта — серверное хранение и синхронизация. Используй безопасную сессионную авторизацию с HttpOnly cookies, CSRF-защитой и корректным завершением сессии. Восстановление пароля должно иметь полноценный серверный сценарий; для production нужна настроенная почта, для разработки — документированный локальный почтовый режим.

Предложи перенос локальных данных в аккаунт явно. Перед объединением покажи, какие записи добавятся, и обработай конфликт с существующими данными. Не передавай гостевые данные автоматически при открытии экрана входа.

### 5. Профили семьи и ограничения

Каждый участник имеет имя или псевдоним, возраст, необязательные параметры роста, веса и активности, цель питания, индивидуальные исключения и предпочтения. Должен быть режим простых порций без ввода антропометрии и без расчёта целей по калориям.

Для взрослого можно предложить ориентировочную норму по документированной формуле с указанием метода и возможностью задать цель вручную. Не обещай медицинскую точность. Для несовершеннолетних и специальных состояний не рассчитывай автоматически дефицит энергии по взрослой формуле: доступно обычное семейное меню и ручные порции.

Разделяй жёсткие ограничения и предпочтения. Исключения ингредиентов, аллергенов и запрещённых категорий должны применяться до подбора рецептов и повторно проверяться перед сохранением. Предпочтения влияют на рейтинг подходящих блюд.

Ограничения должны работать по идентификаторам продуктов и категориям, а не только по совпадению текста названия. Например, запрет риса исключает блюдо с рисом независимо от того, написано ли в названии «плов». Учти состав сложных ингредиентов; рецепт с неизвестным составом нельзя считать проверенным на конкретный аллерген.

Для общего семейного блюда учитывай ограничения всех участвующих в нём людей. Позволь создать отдельную безопасную альтернативу для одного участника. В итоговом меню всегда видно, кому предназначена порция.

Не встраивай медицинские диеты только по названию вроде «Стол №3». Если такие шаблоны появятся позже, правила должны быть отдельно проверены специалистом. Сейчас пользователь задаёт конкретные исключения и разрешённые категории.

### 6. Рецепты и источник данных

Структура рецепта:

- название, собственное описание, категория и подходящие приёмы пищи;
- ингредиенты со ссылками на справочник, количеством, единицей и состоянием продукта;
- число базовых порций и масса готового блюда;
- пошаговое приготовление;
- активное и общее время, обязательное оборудование, допустимые альтернативные способы и сложность с требуемыми техниками;
- КБЖУ на весь рецепт, 100 г и выбранную порцию;
- известные аллергены и полнота данных;
- клетчатка, витамины и минералы при наличии исходных данных, с явными пропусками и пригодностью для режима учёта нутриентов;
- ориентировочная стоимость при наличии данных о ценах;
- условия хранения и возможность заморозки только при наличии проверенных сведений;
- изображение с источником и правом использования либо аккуратная заглушка.

Нужны поиск по названию и ингредиентам, фильтры по категории, времени, исключениям, калорийности и известной стоимости; сортировка и пагинация. Пользователь может добавлять собственный рецепт и редактировать его; пользовательские рецепты приватны по умолчанию.

Создай минимум 40 разных стартовых рецептов и справочник нужных ингредиентов. Должны быть завтраки, вторые блюда, супы, салаты и перекусы, а также варианты без риса, без макарон и без мяса. Это собственная стартовая база, а не копия каталога референса.

Пищевую ценность бери из источника с подходящими условиями использования, сохраняя название источника, состояние продукта, дату и базу измерения. Если сетевой доступ к источнику отсутствует, не выдумывай проверенную базу: используй явно помеченные оценочные стартовые значения, документируй их и реализуй импорт верифицированных данных. Отсутствующий нутриент обозначай null/«нет данных», а не нулём.

Импорт продуктов и рецептов через JSON/CSV должен проходить валидацию, показывать ошибки и не создавать дубликаты при повторном выполнении. Фотографии не скачивай с Youamm. Лучше честная заглушка, чем случайная фотография другого блюда.

### 7. Числовые расчёты

КБЖУ рассчитывай из ингредиентов, используя согласованные единицы и состояние продукта. Отдельно учитывай массу закупаемого продукта, съедобную массу и выход готового блюда. Не подставляй показатели готовой крупы в расчёт сухого ингредиента.

Базовые правила:

- вклад ингредиента = съедобная масса в граммах × показатель на 100 г / 100;
- КБЖУ рецепта = сумма вкладов ингредиентов;
- КБЖУ на 100 г готового блюда = КБЖУ всего рецепта / массу готового блюда × 100;
- вклад порции определяется её долей в готовом блюде;
- округление происходит на этапе отображения, а не при каждом промежуточном вычислении.

Если масса готового блюда неизвестна, не выдавай точное значение на 100 г. Покажи оценку и её основание либо оставь показатель недоступным. Калории источника могут не совпасть строго с формулой 4/9/4 — не исправляй их молча.

При удвоении рецепта ингредиенты и суммарное КБЖУ удваиваются; показатели на 100 г не меняются при том же выходе на единицу рецепта. Семейные порции могут быть разными, но сумма порций не должна превышать приготовленный объём.

Переводы г↔кг и мл↔л универсальны. Переводы массы в объём требуют плотности, в штуки — средней массы штуки, в упаковки — размера упаковки конкретного продукта. Без коэффициента не предлагай преобразование. Дробное количество в рецепте допустимо; округление покупок до упаковок показывай отдельно.

### 8. Генератор меню

Параметры: начальная дата, период от 1 до 35 дней, участники, приёмы пищи, целевые КБЖУ при наличии, исключения, предпочтения, уровень готовки, режим питания, доступная техника, максимальное время готовки, выбранный магазин и ценовой профиль, необязательный бюджет, дни готовки, режим повторяемости и включаемый учёт витаминов.

Обязательные настройки первого релиза:

- **Уровень готовки**: «Начинающий», «Уверенно готовлю», «Любой уровень». У рецепта есть уровень требуемых навыков и отдельное время приготовления. Подбор и замена не предлагают более сложную технику, чем выбрал пользователь. Простое долгое запекание не становится сложным только из-за длительности. Пороговые правила классификации документируй; неизвестную сложность не выдавай за проверенную простоту.
- **Режим питания**: «Обычное» или «Сбалансированное (ПП)». Это предпочтение, отдельное от цели веса, аллергенов и медицинских ограничений. Правила и теги пригодности задаются явно и управляются через справочник; опиши их в `docs/NUTRITION_RULES.md`. Режим ПП влияет на рейтинг подходящих рецептов, не означает автоматически низкую калорийность и не разрешает нарушать запреты. Не делай вид, что воспроизведён неизвестный алгоритм ПП Youamm.
- **Повторяемость**: «Разные блюда каждый день», «Повторы разрешены», «Готовлю на несколько дней». В первом режиме идентичный рецепт не повторяется в выбранном периоде, включая разные приёмы пищи; в остальных пользователь задаёт допустимую частоту и длительность использования партии. Если строгий режим конфликтует с малой базой, закреплёнными блюдами или расписанием готовки, объясни конфликт и предложи изменить настройку. Не включай повторы автоматически.
- **Техника на кухне**: пользователь отмечает доступное оборудование, например плиту, духовку, микроволновку, мультиварку, блендер или аэрогриль. Для рецепта проверяются все обязательные устройства выбранного способа приготовления. Замена устройства допустима только при отдельном описанном способе с соответствующим временем и шагами. Рецепты без нагрева доступны при пустом списке техники.
- **Магазин и бюджет**: сохраняй выбранный магазин, необязательный город/регион ценового профиля и лимит расходов на покупки за период для всей семьи. Предусмотри «Без привязки к магазину». Полный адрес или геолокация не требуются. Подробные правила расчёта указаны в разделе 9.
- **Учитывать витамины**: переключатель должен менять оценку вариантов меню, а не только включать панель отчёта. Требования к данным, нормам и проверкам — в разделе 10. Функция входит в первый релиз.

По умолчанию предлагаются завтрак, обед, перекус и ужин, но пользователь может изменить набор. Предусмотри настройку «обед в контейнер»: по выбранным дням исключаются супы и блюда, не подходящие для перевозки.

Алгоритм:

1. Отобрать допустимые рецепты с учётом состава, участников, оборудования, уровня готовки и времени.
2. Подобрать блюда и реалистичные порции под заданные цели.
3. Оценить разнообразие, режим питания, использование общих ингредиентов, время, стоимость покупаемых упаковок и включённые цели витаминов.
4. Проверить жёсткие ограничения итогового меню.
5. Показать меню, отклонения от целей и причины незаполненных приёмов пищи.

Жёсткие запреты не нарушаются ради попадания в калории или бюджет. Если подходящих рецептов недостаточно, покажи конфликт и предложи изменить мягкое условие. Не добавляй запрещённое блюдо незаметно и не объявляй неудавшийся расчёт успешным.

Задай конфигурируемые допуски к целям по энергии и БЖУ, разумные диапазоны порций и ограниченное время поиска. При цели без КБЖУ используй нормальные базовые порции. Нужен seed генератора для воспроизводимости и диагностики.

Разреши заменять одно блюдо, выбирать рецепт вручную, менять порцию, переносить приём пищи, закреплять выбранные блюда и повторно генерировать только незакреплённые. После изменения сразу пересчитывай нутриенты и покупки.

Поддержи готовку на несколько приёмов пищи. Разделяй партию приготовленного блюда и её последующее употребление: ингредиенты покупаются один раз на партию, а КБЖУ учитывается при каждом фактическом приёме пищи. Готовое блюдо из остатков не превращай повторно в список сырых ингредиентов.

### 9. Покупки, остатки и цены

Список покупок агрегируется по каноническим продуктам и совместимым единицам. Для каждой строки доступны нужное количество, доступный остаток, сколько купить, отдел магазина, отметка покупки и блюда-источники.

Остатки: продукт, количество, единица, место хранения, необязательная дата годности. Используй остатки с подходящими сроками по датам приготовления, а не просто всё, что сейчас записано дома. Учитывай расход хронологически и не используй одну и ту же порцию остатка повторно.

Генерация списка не списывает продукты физически. Раздели плановое резервирование, отметку покупки и подтверждение использования/готовки. Повторное нажатие не должно повторно списывать остаток или создавать вторую покупку.

Можно добавлять свои строки, менять количество, отмечать наличие дома и экспортировать список. При смене меню сохраняй вручную добавленные строки, а устаревшие автоматические строки обновляй предсказуемо. Используй устойчивые идентификаторы и показывай важные изменения.

Поддержи PDF для печати, XLSX для меню и списка покупок, JSON для резервной копии. В XLSX должны быть отдельные листы «Меню», «Покупки» и «Готовка» с читаемыми датами и числовыми количествами.

Стоимость основана на вручную заданных ценах с размером упаковки, датой и валютой. Показывай стоимость использованных ингредиентов отдельно от стоимости покупки упаковок. При отсутствии цены итог помечай как неполный. Не изображай реальные цены магазинов, доставку или автоматическую экономию без источника.

Добавь справочник магазинов и сохраняемый ценовой профиль пользователя. Выбор «Пятёрочка» или другой сети сам по себе не загружает реальные цены и остатки. В первом релизе цены и необязательная доступность товара вводятся вручную или импортируются из пользовательского JSON/CSV с источником и датой; исходные цены остаются неизвестными до ввода. Не показывай фиктивную заполненную корзину внешнего магазина и не обещай заказ или доставку. Собственный список Foodo может называться «Корзина покупок» с ясным указанием, что это список внутри приложения.

Когда указан бюджет, оценивай фактическую стоимость покупки упаковок с учётом доступных домашних остатков. Расчёт относится ко всей выбранной семье и точно указанному периоду; показывай сумму, лимит, разницу и полноту цен. Если все цены известны, превышающий лимит вариант не считается соответствующим бюджету. При неполных ценах показывай «Бюджет не подтверждён», перечисляй недостающие цены и не утверждай, что меню уложилось в лимит. Если допустимое меню не находится, объясни, что в пределах текущего поиска и данных не найден подходящий вариант; не объявляй математическую невозможность без доказательства и не уменьшай порции до нереалистичных значений.

Смена магазина или ценового профиля пересчитывает стоимость, статус бюджета и доступность по известным данным. Пользовательские исправления списка покупок сохраняются. Не меняй закреплённые блюда без явного действия пользователя.

### 10. Вода, привычки и нутриенты

Вода: индивидуальная ручная цель, добавление и отмена записи, итог дня, история. Даты определяются часовым поясом пользователя. Не смешивай воду нескольких участников.

Привычки: пользователь задаёт простую привычку, отмечает выполнение и смотрит историю. Напоминания необязательны и не блокируют основные функции.

Клетчатку, витамины и минералы показывай только при наличии данных, с единицами и указанием полноты расчёта. Не выводи 100% выполнения нормы при неизвестной части ингредиентов. Не назначай добавки по результатам меню.

В первый релиз входит режим **«Учитывать витамины»** с реальным влиянием на генератор. Начальный поддерживаемый набор: витамины A, C, D, E, B6, B12 и фолат. Минералы отображаются при наличии данных, а их включение в оптимизацию настраивается отдельно после появления проверенных целевых значений и достаточного наполнения базы. Этот перечень — решение для Foodo, а не подтверждённый состав функции Youamm.

Для каждого поддерживаемого витамина храни единицу, форму/эквивалент, источник, полноту исходных данных и версию целевой нормы. Совместимость единиц и форм проверяй; не складывай автоматически разные эквиваленты витамина A или фолата. Цели импортируй из проверенного применимого справочника с условиями использования либо задавай вручную. Не придумывай числовые нормы, коэффициенты сохранности при готовке или верхние уровни потребления. Запиши источники и ограничения в `docs/NUTRIENTS.md`; где норм или данных нет, функция показывает точную причину недоступности соответствующего показателя.

При включении режима оценивай отклонения от выбранных витаминных целей по каждому участнику на уровне периода планирования, сохраняя суточный отчёт. Покрытие сверх целевого уровня не должно приносить дополнительный балл; не подбирай чрезмерные порции ради витаминов. Все исключения, реальные порции, оборудование и проверяемый бюджет сохраняют приоритет. Используй проверенные пределы только когда они действительно есть в справочнике, не делай медицинских выводов по результатам оптимизации.

Учитывай известный состав, состояние продукта и доступные данные по приготовлению. Недостаточную полноту показывай как ограничение расчёта, а не доказательство отсутствия витамина. При неполной базе оценивай только пригодные для этого показатели и явно сообщай, какие цели не удалось проверить. Нельзя заменять эту функцию декоративным переключателем или отключать её полностью под видом будущего расширения: реализуй расчёт, загрузку справочников, тестовый пример с полными данными и демонстрацию влияния на выбор меню. Непроверенные стартовые значения разрешены только в явно обозначенном демонстрационном сценарии; для реальных профилей не выдавай их за подтверждённые нормы.

### 11. Модель данных и права доступа

Спроектируй сущности пользователей, домохозяйств, участников, членства и ролей, продуктов и их состава, единиц и коэффициентов, нутриентов и версий целевых норм, рецептов и версий, ингредиентов, шагов, исключений, предпочтений и режимов подбора, уровней навыков, оборудования и альтернативных способов приготовления, магазинов и пользовательских ценовых профилей, меню и приёмов пищи, порций, партий готовки, остатков, списков покупок, цен, избранного, воды, привычек и статей.

Сохраняй снимок рецепта или ссылку на конкретную версию в меню, чтобы правка публичного рецепта не меняла незаметно старое меню и список покупок.

У семьи — владелец и явно приглашённые участники. Все запросы к приватным данным проверяют права на сервере. Идентификатор в URL не является разрешением доступа. Административные возможности недоступны обычному пользователю.

Для гостевых данных нужен versioned JSON-формат с миграциями локального хранилища. Обновление PWA не должно уничтожать сохранённое меню.

### 12. Безопасность и эксплуатация

Реализуй валидацию ввода, безопасное хранение паролей средствами Django, CSRF, ограничение частоты входа и тяжёлых операций, ограничения объёма импорта и генерации, безопасный вывод пользовательского контента. Не публикуй секреты, конфигурацию production и персональные данные в логах или клиентском JavaScript.

У аккаунта доступны экспорт своих данных и удаление аккаунта с понятным подтверждением. Приватные данные не становятся общедоступными вследствие бесплатности сервиса. Документы об обработке данных подготовь как шаблоны с полями владельца, не копируй реквизиты и документы Youamm и не объявляй юридическое соответствие автоматически доказанным.

PWA должно иметь manifest, собственные иконки, service worker, экран без сети и понятную процедуру обновления. В гостевом режиме офлайн работают загруженный каталог, меню и покупки. Для аккаунта в первом релизе офлайн — чтение ранее загруженных данных; изменение серверных данных требует сети, это видно в интерфейсе. Не реализуй скрытую синхронизацию с возможной потерей изменений.

Не кешируй чужие приватные ответы или сессии; очищай приватный кеш при выходе. HTTPS нужен для публичной установки PWA. Push-уведомления не включаются без отдельного выбора пользователя и не должны быть обязательны.

### 13. GitHub Actions и развёртывание

Подготовь CI: линтеры, backend-тесты с PostgreSQL, TypeScript-проверка, тесты расчётов frontend, сборка, интеграционные сценарии. Сборка создаёт Docker-образы и пригодные для скачивания артефакты. Публикация образов — по явно настроенному workflow с минимальными разрешениями.

Добавь .env.example без секретов, миграции, команду загрузки стартовых данных, создание администратора, health checks, конфигурацию прокси и документированный production Docker Compose. Приложение должно переживать перезапуск контейнеров без потери БД и пользовательских файлов.

Дай пошаговую инструкцию: создать репозиторий → добавить код → пройти CI → настроить сервер, домен и секреты → выполнить миграции и загрузку данных → запустить → проверить HTTPS и основные сценарии. Опиши резервное копирование, восстановление и безопасный порядок обновления БД.

Без предоставленного сервера и домена не заявляй о публичном запуске. Разделяй «проект собран», «тесты пройдены» и «сервис развёрнут». GitHub Actions используется для сборки, а работающий backend и PostgreSQL требуют среды исполнения. Бесплатность для пользователей не означает отсутствие расходов владельца на инфраструктуру.

### 14. Обязательные проверки

Проверь минимум следующие сценарии:

1. Гость без аккаунта создаёт семью из двух взрослых, меню на 7 дней и список покупок; данные сохраняются после перезагрузки.
2. Запрет риса и макарон исключает их из ингредиентов, замен и покупок, независимо от названия блюда.
3. Аллерген одного участника исключён из общего блюда; альтернативы не наследуют запрещённый ингредиент.
4. При увеличении порций вдвое ингредиенты и КБЖУ рецепта удваиваются, а КБЖУ на 100 г остаётся прежним при неизменном относительном выходе.
5. Разные семейные порции дают разные КБЖУ, их сумма согласована с партией приготовления.
6. После замены блюда пересчитываются меню и покупки; вручную добавленные покупки сохраняются.
7. На рецепт нужно 800 г картофеля, дома доступно 300 г: к покупке 500 г. Если остаток просрочен к готовке, он не вычитается.
8. Партия на два обеда закупается один раз, но порции учтены в двух приёмах пищи.
9. Без плотности нельзя автоматически преобразовать граммы продукта в миллилитры; без массы штуки нельзя выдавать точный перевод в штуки.
10. Несовместимые ограничения дают понятное объяснение, а не меню с запрещённым продуктом.
11. При отсутствии цены или нутриента показывается неполнота данных; неизвестное не превращается в ноль.
12. Пользователь A не может прочитать или изменить семью, меню, остатки и покупки пользователя B, в том числе прямым запросом API.
13. Повторный импорт стартовых данных и повторное подтверждение операции не создают дубликаты и двойной расход.
14. Гостевой JSON экспортируется и импортируется без потери данных; перенос в аккаунт обрабатывает конфликт явно.
15. PDF и XLSX открываются и содержат реальные актуальные количества и русские тексты.
16. Смена часового пояса и переход суток корректно разделяют записи воды и даты меню.
17. Основной путь работает на телефоне шириной 360 px, с клавиатуры и после установки PWA.
18. Данные гостя не отправляются на сервер при генерации; при выходе очищаются приватные кеши аккаунта.
19. После изменения рецепта сохранённое меню сохраняет прежнюю версию и значения.
20. Меню на 35 дней формируется за ограниченное время либо сообщает о невозможности подбора без зависания.
21. Начинающий с одной плитой получает доступные ему по технике блюда; рецепт, требующий духовку или сложный приём, не проходит фильтр и замену. Заданная альтернативная техника корректно меняет шаги и время.
22. Режимы ПП и обычного питания сохраняются и влияют на рейтинг в контролируемом примере; отключение ПП не отменяет аллергенов и стоп-продуктов.
23. «Разные блюда каждый день» исключает повторы одного рецепта за выбранный период. Конфликт с размером каталога, закреплениями или партией на несколько дней объясняется явно.
24. Выбранный магазин и ценовой профиль сохраняются; их смена пересчитывает стоимость. При неизвестных ценах статус бюджета остаётся неподтверждённым.
25. Если нужно купить две упаковки по 100 ₽ при лимите 150 ₽, меню не объявляется укладывающимся в бюджет, даже если стоимость съедаемой части меньше 150 ₽.
26. В фиксированном наборе вариантов с полными тестовыми нутриентами включение учёта витаминов выбирает меню с лучшим покрытием при одинаковых запретах, допустимых порциях и прочих условиях. Одинаковый результат на произвольных данных сам по себе не является ошибкой.
27. Пропуски нутриентов, отсутствие целевой нормы и несовместимые единицы не превращаются в нулевое содержание или доказанное выполнение цели. Демонстрационные нормы не используются незаметно для реальных профилей.

Нужны unit-тесты числовых правил, интеграционные тесты API и прав, а также несколько E2E-тестов основных сценариев. Не заменяй их одним тестом существования компонентов.

### 15. Порядок реализации и готовность

Начни с кратких принятых решений, модели данных и плана. Затем сразу создавай проект. Рутинные технические решения принимай самостоятельно; вопросы задавай только при настоящем препятствии, например отсутствии целевого репозитория или инфраструктуры для публикации.

Реализуй последовательно:

1. Каркас, справочники, стартовые данные и расчёты.
2. Полный гостевой сценарий: семья → меню → рецепты → покупки → сохранение → экспорт.
3. Аккаунт, перенос данных, права и синхронизация.
4. Остатки, партии готовки, настройки навыков/питания/техники/повторов, магазин и бюджет, подбор с витаминами, вода, привычки, статьи и административное управление.
5. PWA, доступность, CI, эксплуатационные документы и итоговые проверки.

Этапы — порядок работы, а не основание закончить после первого экрана. Для первого релиза должны быть выполнены все перечисленные основные функции, включая настройки из роликов и рабочий режим учёта витаминов с честной доступностью исходных данных. Нельзя считать готовым проект с декоративными кнопками, статическим меню вместо генератора, сохранением только в памяти, выдуманными расчётами, заглушкой сервера или незавершёнными основными сценариями. Стартовые данные и отсутствующие фотографии могут быть честно обозначены; сама логика должна работать.

Если задача не помещается в один ответ, сохраняй прогресс в репозитории и docs/STATUS.md, где указаны реализованные возможности, реальные результаты тестов и следующие шаги. Не обещай, что весь сложный продукт гарантированно будет завершён одним сообщением. При наличии рабочей среды продолжай реализацию до выполненных критериев; при лимите ответа выдавай точный запрос для продолжения с сохранённого состояния.

## Согласованные решения владельца (16 октября 2026 года)

1. **Ветки и релиз.** Начальный коммит в `main`, работа через pull request; после зелёного CI PR сливается, релиз выпускает workflow GitHub Actions. На компьютере владельца ничего не устанавливается и не собирается.
2. **Подпись релизов.** Sigstore-аттестации GitHub Actions (`actions/attest-build-provenance`), без собственных ключей; проверка — `gh attestation verify`.
3. **Сайт.** Для тестов и разработки — GitHub Pages в гостевом режиме (все функции без аккаунта, данные в браузере). Для production позже — собственный сервер: Docker-образы в GHCR и инструкция `docs/DEPLOYMENT.md`.
4. **Нормы витаминов.** Значения МР 2.3.1.0253-21 для взрослых внесены со статусом «не сверено с первоисточником» до проверки владельцем.
5. **Дизайн.** Максимально современный, удобный и стильный: собственная палитра, крупная выразительная типографика (Onest), карточки-«бенто», полноценная тёмная тема, сдержанные микроанимации, режим готовки с крупными шагами.
6. **Минимум действий.** Каждый сценарий проектируется под наименьшее число нажатий: быстрый старт в два шага с разумными значениями по умолчанию, автосохранение, отмена вместо подтверждений, замена блюда в одно касание, автоматический список покупок, вода в одно касание. Подробнее — раздел «Принципы интерфейса» в `docs/ARCHITECTURE.md`.
7. **Лицензия** не выбрана: публикация исходников под открытой лицензией — отдельное решение владельца, файл лицензии не добавлен.
8. **Города и магазины.** Все ~1100 городов РФ (справочник городов с регионом и часовым поясом). Город определяется геолокацией на устройстве: координаты не покидают браузер, ближайший город выбирается локально; ручной выбор всегда доступен. Предлагаются крупные федеральные и региональные сети, присутствующие в регионе (присутствие — по открытым данным, статус «не сверено»).
9. **Цены.** Три источника вместе: средние цены Росстата по регионам (оценка, помечается «≈»), анонимные цены пользователей (медиана по городу и сети, без профилей и меню) и сбор цен с сайтов сетей в GitHub Actions с соблюдением robots.txt и ограничением частоты. Собственные цены семьи всегда важнее публичных. Если сайт сети недоступен или запрещает сбор, это показывается, а не подменяется.
10. **Рецепты.** Около 300 настоящих блюд с реальными рецептами (ингредиенты, граммовки, шаги). Фотографии — из Wikimedia Commons, загружаются workflow GitHub Actions, с автором, лицензией и ссылкой; без подходящего фото показывается заглушка.
11. **Android (17 октября 2026 года).** Готовый APK в GitHub Releases: гостевая версия сайта в оболочке Capacitor (не отдельное нативное приложение), пакет `io.github.lucky2356.foodo`. Подпись — ключом из секретов репозитория в GitHub Actions. Автообновление из GitHub Releases с проверкой SHA-256, пакета, версии и сертификата подписи перед установкой. versionCode = X·10000 + Y·100 + Z из `VERSION`. Подробности — `docs/ANDROID.md`.
12. **Анкета перед меню (17 октября 2026 года).** Пользователь сначала задаёт настройки, затем получает меню: анкета из шагов «семья → цель → тип питания → запреты → вкусы → кухня и время → план → сводка» заменяет быстрый старт в два шага (решение 6 уточнено). Ответы подставляются из существующей семьи, анкету можно пройти заново.
13. **Больше качеств, влияющих на меню.** Типы питания участника (жёсткие запреты по составу), переносимость остроты (жёсткая проверка, у детей по умолчанию «без остроты»), лимит времени на выходные, любимые кухни и продукты, режим «Больше белка», предпочтение детских блюд. Правила режимов — `docs/NUTRITION_RULES.md`.
14. **Каталог 1000 рецептов.** 8 категорий, включая десерты, выпечку и напитки. Фото — из Wikimedia Commons и Openverse только под свободными лицензиями, каждое проверяется визуально; без подходящего фото — рисованная обложка, которая не выдаётся за фотографию (решение 10 расширено).
15. **Палитры.** Светлая тема «Свежая зелень и манго»: зелёные кнопки и выбранные состояния, манговые акценты, кремовый фон. Тёмная тема «Глубокий чёрный»: фон #000, карточки #141414, действия — манго, зелёный — только редкий акцент.
16. **Экраны от HD до 4K и анимации.** Раскладка от 360 px до 4K (на очень широких экранах интерфейс масштабируется), анимации переходов и появления, которые отключаются системной настройкой «Уменьшить движение».

# Архитектура Foodo

## Обзор

```
Браузер (React PWA)
 ├─ Гость:   UI → GuestGateway → TS-движок → IndexedDB «foodo-guest»
 │            публичные данные: каталог (в сборке), цены (data/prices/*.json или /api/prices/public)
 └─ Аккаунт: UI → RemoteGateway → /api (Django) → Python-движок → PostgreSQL
              копия для чтения офлайн: IndexedDB «foodo-cache-account-<id>», удаляется при выходе
```

UI работает с одним интерфейсом `Gateway` (`frontend/src/data/types.ts`). Гостевая и серверная реализации выполняют одни и те же операции: семья, меню, покупки, остатки, цены, избранное, вода, привычки, экспорт.

## Модули

| Модуль | Ответственность |
| --- | --- |
| `frontend/src/engine/`, `backend/engine/` | Чистая доменная логика без HTTP, ORM и UI: единицы, КБЖУ, проверка запретов, генератор, операции над меню (замена, закрепление, порции), покупки, отчёт, витамины, энергия. Две реализации с одинаковыми правилами. |
| `shared/data/` | Стартовые справочники с устойчивыми идентификаторами: категории (иерархия), аллергены, оборудование, техники, навыки, теги ПП, отделы магазина; продукты; рецепты с версиями; нормы витаминов; статьи; города и сети. |
| `shared/fixtures/engine/` | 8 сценариев (`cases.json`) и ожидаемые результаты. TS-тесты и Python-тесты сравнивают свой вывод с одними файлами — это доказательство паритета. |
| `frontend/src/data/` | `localDb.ts` (схема IndexedDB, версии), `guestGateway.ts`, `remoteGateway.ts`, `backup.ts` (версионированный JSON-экспорт/импорт), `geo.ts` (город по геолокации на устройстве), `prices.ts`. |
| `frontend/src/pages/`, `ui/`, `state/` | Экраны, компоненты, состояние приложения. Формул в обработчиках нет — только вызовы движка/шлюза. |
| `frontend/src/export/` | Модель экспорта (одна для PDF и XLSX), PDF с DejaVu (кириллица), XLSX с листами «Меню», «Покупки», «Готовка»; защита от формул. |
| `backend/catalog` | Каталог, версии рецептов, импорт JSON с валидацией, админка с импортом, публичный API каталога. |
| `backend/accounts` | Регистрация, вход, выход, сброс и смена пароля, экспорт и удаление аккаунта. Сессии Django, HttpOnly cookies, CSRF. |
| `backend/households` | Семьи, роли (`owner`, `editor`, `viewer`), приглашения, участники, меню, покупки, партии, остатки, свои цены, избранное, вода, привычки, перенос данных гостя. |
| `backend/geo` | Города (≈1100, регион, часовой пояс, координаты) и торговые сети с регионами присутствия. |
| `backend/prices` | Публичные наблюдения цен (`rosstat`, `scraped`, `community`) и выбор цены для города/сети. |

## Данные

### Каталог

- **Продукт**: `id`, категория (с предками), аллергены, состояние (`raw`, `dry`, `cooked`…), базовая единица (`g`/`ml`/`pcs`), доля съедобной части, масса штуки, плотность (только если известна), упаковки, нутриенты на 100 г с источником и статусом проверки. Неизвестное значение — `null`, не ноль.
- **Рецепт**: категория блюда, приёмы пищи, ингредиенты (продукт, количество, единица, съедобная масса), выход готового блюда, порции, теги ПП, техники (навык рассчитывается из них), способы готовки (`methods`: оборудование, шаги и время у каждого способа), пригодность для контейнера и хранения, `version`.
- **Версии рецептов** хранятся (`RecipeVersion`). Меню содержит снимок рецептов и продуктов (`menu.snapshot`), поэтому правка рецепта не меняет сохранённую неделю и покупки.

### Пользовательские данные (сервер)

`Household` → `Membership` (пользователь, роль) / `Member` (участник питания: возраст, пол, вес, рост, активность, цель, режим порций, ограничения, предпочтения, часовой пояс, цель по воде) / `Menu` (документ движка в JSON + состояние покупок с ревизией) / `CookConfirmation` и `PurchaseTransfer` (уникальные ограничения на партию и строку — повтор и конкуренция не списывают дважды) / `PantryItem` / `PriceEntry` / `Favorite` / `WaterEntry` / `Habit`, `HabitMark`.

### Гость (IndexedDB `foodo-guest`, `DB_VERSION = 1`)

Хранилища: участники, настройки семьи, меню, состояние покупок, остатки, цены, избранное, вода, привычки, свои рецепты. Формат экспорта `foodo-guest-export`, `format_version = 1`; `migrateExport` переносит старые версии и отклоняет более новые. Обновление PWA не трогает IndexedDB.

## Генератор меню

1. **Фильтр** (жёсткий): ограничения каждого участника блюда по замыканию состава (категории с предками, аллергены; неизвестный состав = нарушение), тип приёма пищи, наличие оборудования для хотя бы одного способа, навык (ранг по техникам; неизвестная сложность скрыта от начинающих), время, обеды в контейнер, режим повторяемости.
2. **Оценка**: правила ПП/обычного режима (`reference.diet_rules`), любимое/нелюбимое, разнообразие категорий за день, повторное использование, общие ингредиенты, время готовки, оценка стоимости (если задан бюджет), прирост покрытия витаминов (если включено), небольшой детерминированный шум от seed.
3. **Порции**: простой коэффициент или цель энергии участника по долям приёмов пищи, в границах реалистичных порций.
4. **Несколько попыток** с seed (mulberry32); лучшая по целевой функции. Незаполненный слот или известное превышение бюджета штрафуются и показываются, а не скрываются.
5. **Финальная проверка** меню на жёсткие ограничения; при невозможности подбора — объяснимый конфликт (`unfilled` с причинами: техника, навык, запрет участника, повторы).

Режимы повторяемости: `unique` — идентичный рецепт не повторяется за период (конфликт объясняется), `allow` — повторы с штрафом, `batch` — готовка партиями (одна партия на несколько приёмов пищи по дням готовки).

Ограничение стоимости поиска: `SCORE.maxEvaluations` и число попыток по длительности периода; на сервере также throttling генерации.

## Покупки и остатки

- Потребность считается **на партию** (сырые ингредиенты один раз), нутриенты — по съедаемым порциям.
- Остатки распределяются по дате готовки (FIFO по сроку годности, только годные к дате); один остаток не покрывает две потребности.
- Строка покупки: потребность, покрыто остатками, купить, упаковки (по размеру упаковки продукта), стоимость упаковок и стоимость использованного — раздельно.
- Ручные строки и отметки хранятся отдельно от автоматических и переживают пересчёт; автоматические строки имеют устойчивый `id` (продукт + единица) и источники потребности.
- «Приготовлено» списывает остатки один раз на партию; «перенести купленное» добавляет остаток один раз на строку.
- Деньги — целые копейки. Статус бюджета: `none`, `ok`, `exceeded`, `unconfirmed` (если у части строк нет цены).

## Цены

Приоритет: свои цены семьи → цена сети в городе (сбор с сайта) → медиана анонимных цен пользователей → средняя Росстата по региону (оценка, «≈»). Подробности — [`PRICES.md`](PRICES.md).

## API

OpenAPI-схема: `/api/schema/`, Swagger UI: `/api/docs/`. Ошибки: `{"code": "<stable_code>", "message": "<русский текст>", "fields": {...}}`.

- Публичные: `/api/health/`, `/api/catalog/{bundle,recipes,products,articles}/`, `/api/geo/{cities,chains}/`, `/api/prices/public/?city=&chain=`.
- Аккаунт: `/api/auth/{csrf,register,login,logout,me,session,password/reset,password/reset/confirm,password/change}/`, `/api/account/{export,delete}/`, `/api/invitations/accept/`. `session` всегда отвечает 200 (`{"user": … | null}`) — им пользуется запуск приложения, чтобы гость не получал 403; `me` требует входа.
- Семья: `/api/households/<id>/…` — `members`, `invitations`, `menus` (+ `ops`, `candidates`, `shopping`, `shopping/transfer`, `batches/<bid>/cook`, `report`), `pantry`, `prices`, `favorites`, `recipes`, `water`, `habits` (+ `marks`), `import-guest`.

Доступ проверяется на каждом запросе по членству и роли; чужой ID семьи даёт 404. Приватные ответы — `Cache-Control: no-store`. Ограничения частоты: вход, регистрация, сброс пароля, генерация, импорт, публикация цен.

## Безопасность и приватность

- Гостевой генератор работает в браузере; в сеть уходят только ID города и сети (для цен). Тест перехвата запросов это проверяет.
- Геолокация: координаты используются только на устройстве для выбора ближайшего города.
- Сессии Django + HttpOnly cookies, CSRF, `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE` в production, HSTS через Caddy и Django.
- Service worker кеширует только оболочку приложения и публичный каталог. Приватные ответы API не кешируются; копия аккаунта для офлайн-чтения удаляется при выходе.
- CSP и прочие заголовки — `deploy/nginx-security-headers.conf`.

## Android-приложение

`frontend/android/` — проект Capacitor 8 вокруг гостевой сборки (`vite build --mode android`: то же, что статическая сборка с той же CSP в meta-теге, но без service worker и с флагом `__FOODO_NATIVE__`). Код только для приложения лежит в `frontend/src/native/` и подключается лениво за флагом `NATIVE_BUILD`, поэтому веб-сборки его не содержат.

- Плагин `FoodoUpdater` (Java): проверка GitHub Releases, загрузка, проверка SHA-256, пакета, versionCode и сертификата, установка через PackageInstaller. Правила выбора релиза — в `UpdatePolicy` (чистая Java без Android, unit-тесты). JavaScript не передаёт плагину адреса: он скачивает только релиз, принятый последней проверкой.
- Плагин `FoodoFiles`: сохранение экспортов через системное окно «Сохранить» (WebView не умеет скачивать blob:-ссылки).
- Подробности, проверки и сборка — `docs/ANDROID.md`.

## Принципы интерфейса

Цель — минимум действий пользователя:

1. **Анкета перед меню**: семья, цель, тип питания, запреты, вкусы, кухня и время, план → сводка → меню. У каждого шага разумные значения по умолчанию, поэтому анкету можно пройти кнопкой «Дальше»; всё меняется позже в профиле и настройках.
2. **Автосохранение** всех изменений; кнопки «Сохранить» нет там, где её можно избежать.
3. **Отмена вместо подтверждений**: замена, перенос и удаление блюда выполняются сразу, тост предлагает «Отменить» (отмена возвращает блюдо с порциями, закреплением и партией; отменить можно только последнее изменение). То, что нельзя вернуть без потерь — удаление участника, меню, своего рецепта, восстановление из файла, — подтверждается.
4. **Замена блюда в одно касание** с подбором по тем же правилам; закрепление — тоже одно касание.
5. **Список покупок собирается сам** из меню, по отделам магазина, за вычетом остатков. Бюджет сверяется с текущим лимитом семьи. «Купленное — в остатки» переносит целые упаковки; эти количества (`PurchaseTransfer.qty`, у гостя `transferred_qty`) не считаются «уже дома» для списка того же меню, поэтому список и бюджет после переноса не меняются, а другие меню видят продукты в остатках.
6. **Вода в одно касание** с главного экрана.
7. **Город и магазин** определяются на устройстве; выбор можно изменить.
8. Работа при ширине 360 px, клавиатура, видимый фокус, подписи полей, тёмная тема, офлайн-состояние.

## Важные решения

- **Два движка (TS и Python)** вместо одного: гостевой режим обязан работать без сервера и без передачи профилей. Паритет обеспечен общими фикстурами, одинаковым порядком операций с плавающей точкой и seed-генератором mulberry32.
- **Hash-роутер и `base: './'`**: статическая сборка работает в подкаталоге GitHub Pages без серверных правил.
- **Меню как JSON-документ** в PostgreSQL: формат совпадает с гостевым, перенос гостя в аккаунт и экспорт не требуют преобразований; согласованность изменений обеспечивают ревизии и транзакции.
- **Без Redis и очередей**: кеш throttling в таблице БД, тяжёлые операции ограничены по размеру.
